# Changelog

## Unreleased

- The access file writes `credentials.unrestricted_credential_count` and `write_access_credential_count` from the audit level, and `unrestricted_pct` and `write_access_pct` at every level, in total and for each scope. Each active access key is evaluated by its IAM user's identity policies: the managed policies attached to the user and its groups, read at their default version, and their inline policies. A key is unrestricted when an allow of every action on every resource holds with no deny taking any of it back, and no source limit applies: a deny of every action with a `NotIpAddress` condition on `aws:SourceIp`, or an `IpAddress` condition on `aws:SourceIp` on every allow. A set of addresses that holds `0.0.0.0/0` or `::/0` limits nothing. A key can write when it is allowed an action whose name after the service prefix does not start with Get, List, Describe, Head, BatchGet, Search, Lookup, Scan, Query, Select, or View. The AWS managed `ReadOnlyAccess`, `ViewOnlyAccess`, and `SecurityAudit` policies are read-only and are not read. A deny of every action on every resource with no condition leaves a key nothing. Requests signed with an access key carry no MFA, so the MFA conditions are evaluated as absent, and no other condition but `aws:SourceIp` is evaluated. A user with a permissions boundary leaves out each value its identity policies allow, with a `not_read` gap, and a failed read leaves out the values it could change with its gap. Service control policies are not read. The reads use `iam:GetPolicy`, `iam:GetPolicyVersion`, `iam:GetUserPolicy`, `iam:GetGroupPolicy`, and `iam:GetUser`, which the trust-level policy in `docs/configuration.md` now grants, and the policy listings the admin check makes, for each IAM user with an active access key, at every level unless `collect` leaves out `access-posture`. Through v0.8.4 the four values were left out with a `not_read` gap.
- The access file's credentials count the root user's active access keys, which are unrestricted and can write, in `credential_count` and every credential percentage. cloud-posture's deprecated `iam.access_key_user_count` and `access_key_rotation_compliant_pct` count the root user among the users with an active access key, as their definitions name every such user. The detailed file's `iam.access_key_user_count` and `access_keys_rotated` still count the IAM users alone. Through v0.8.4 the root user's keys were left out of all of them.
- cloud-posture's `backup.retention_days_min` is the shortest retention among the databases that keep automated backups, and null when none does. A database whose retention period is 0 days has automated backups off. The detailed file's `rds.backup_retention_min` still counts it as 0. Through v0.8.4 a database with backups off made the minimum 0.

## v0.8.4

- The collector is built on epack v0.12.2.
- The access file writes `connected_apps`. A connected app is an AWS account outside the organization that an IAM role's trust policy lets assume the role without MFA, and `app_count`, from the audit level, counts each such account once across every role in every account collected. A trust policy statement with a `Bool` condition that `aws:MultiFactorAuthPresent` is true, or a numeric condition on `aws:MultiFactorAuthAge`, lets in people signing in from the other account, so an account only such statements admit is not counted. `BoolIfExists` does not require MFA, since it lets requests signed with access keys through, and an account that any other statement admits, such as one with an `sts:ExternalId` condition, is counted. The organization's accounts come from `organizations:ListAccounts`, which is optional and best effort and is now called at every level, as is the listing of every role, unless `collect` leaves out `access-posture`. A role that trusts only its own account, a service principal, or a SAML or OIDC provider, such as IAM Identity Center's `AWSSSO_` provider or a GitHub Actions OIDC provider, adds none, and neither does an account the run collects or an IAM Identity Center application. When the role listing fails, both values are left out with its gap. When a role lets another account in without MFA and `ListAccounts` fails, they are left out with its gap, and when a role lets every principal, `*`, in without MFA, with a `not_read` gap, since its trust policy's other conditions are not evaluated. `apps_present` is still true when an account is known to be outside. The detailed file's role rows still list every account a role trusts. Through v0.8.3 `connected_apps` was left out with a `not_read` gap.

## v0.8.3

- The collector is built on epack v0.11.3.
- cloud-posture leaves `storage.network_restricted_pct` out with an `unsupported` gap, and `network_restricted_storage_resource_count` from the audit level, since S3 has no setting that turns off public network access for a bucket or an account. epack v0.10.6 added both values to the schema.

## v0.8.2

- cloud-posture's deprecated `iam.user_count` and `iam.mfa_coverage_pct` count the IAM users with a console password, who can sign in, as their access-posture replacements `members.local_member_count` and `local_mfa_coverage_pct` do. A user with only access keys is left out. The detailed file adds those users as `iam.console_user_count`, `console_mfa_user_count`, and `console_mfa_enabled`.
- cloud-posture writes `database.public_access_blocked_database_count` from the audit level, and `public_access_blocked_pct` over the databases. A DB instance outside a cluster has public access blocked when it is not publicly accessible, and a DB cluster when none of its instances is. The detailed file adds `rds.public_access_blocked_database_count` and `public_access_blocked`.
- Each account in the access file's `scopes` counts its IAM Identity Center users as `members.sso_member_count`: the users ListAccountAssignments assigns to the account, directly or through a group, read from the account that holds the organization instance. The account's `member_count` adds them and `sso_coverage_pct` is their share. The account's admin and inactive values are left out with a `not_read` gap only when Identity Center users are assigned to it. When Identity Center has no users, every account's count is 0.

## v0.8.1

- An ECS service on a capacity provider strategy counts in `fargate_service_count` when its strategy uses the `FARGATE` or `FARGATE_SPOT` provider. DescribeServices gives such a service no launch type. Each service row adds `capacity_providers` and `fargate`, and `fargate_service_count` counts the rows with `fargate` true. A service with neither a launch type nor a strategy leaves `fargate_service_count` out with an `invalid_response` gap.
- `ecs.cluster_count` counts every cluster that ListClusters returns, including a cluster that runs no service.
- An EC2 instance row's `root_volume_encrypted` is false for an unencrypted root volume. When DescribeVolumes does not list the instance's root volume, the value is left out with an `invalid_response` gap.
- `account_security.inspector.enabled` is Inspector's own status in the primary region, read with `BatchGetAccountStatus`. It is true when Inspector is on with no findings, or with Security Hub off. cloud-posture's `vuln_scanning.enabled` copies it. `status_evaluated` and `status_error_code` describe the read of Inspector's findings in Security Hub. A run whose `collect` leaves out `vuln-scanning` still calls `inspector2:BatchGetAccountStatus`, once, in the primary region.
- Each CIS level's `enabled` is true when Security Hub has a CIS standard enabled, including one whose controls have no findings yet.
- `security_hub.auto_enable_controls` is written as false when Security Hub leaves new controls off. When DescribeHub leaves the setting out, it is left out with an `invalid_response` gap.
- The overview says that AWS Config and Security Hub are read in the primary region only.

## v0.8.0

- In the access file, the members are the IAM users with a console password and the users of the organization's IAM Identity Center, so `member_count` adds `sso_member_count` to the IAM users, and `sso_coverage_pct` is written as their share. An IAM user with access keys and no console password is a credential, not a member, and is not checked for admin access. When Identity Center has users, the inactive member values, and each account's `member_count`, are left out with a `not_read` gap.
- Admins are the IAM members with the AWS managed `AdministratorAccess`, `PowerUserAccess`, or `IAMFullAccess` policy, on the user or one of the user's groups. A user with an inline or customer managed policy and none of those three leaves the admin counts out with a `partial` gap, since the collector does not read policy documents. The collector reads inline policy names with the new `iam:ListUserPolicies` and `iam:ListGroupPolicies` calls. When Identity Center has users, `admin_count` and `admin_share_pct` are left out with a `not_read` gap, and the `local_admin_*` values still count the IAM admins.
- The collector is built on Go 1.26.11.

## v0.7.3

- The collector is built on epack v0.10.5.
- A trust-level run no longer writes an identifier of your accounts or resources. The detailed file's `accounts[*].account_id`, `iam.root_organization_id`, `account_security.guardduty.finding_notification.administrator_account_id`, `identity_center.instance_arn`, `instance_owner_account_id`, and `identity_store_id`, and `failed_accounts[*].account_id` and `role_arn` are written from the audit level. The schema marks them `audit` and stays at 1.0.0. A reader of a trust artifact that keyed accounts by `account_id` needs `account_label` or the account's position.
- At trust, `diagnostics.account_errors` and `warnings` name an account by its configured label, as `(default credentials)`, or by its position in the configuration, give a failed call's AWS error code in place of AWS's message, and say what kind of resource a warning is about without its name or ID. Audit and internal runs write them as before.
- The collector result lists the run's targets: the accounts from `aws.cloud-posture.json` and each account's regions from `aws.details.json`. It declares each account's primary region separately, for the AWS Config, Security Hub, and `account_security.inspector` values read there alone. That region is the new `accounts[*].primary_region` in `aws.details.json`. A trust run gives no counts.

## v0.7.2

- The collector is built on epack v0.10.2.
- The deprecated `accounts[*].iam` and `workforce_sign_in` blocks are left out when `collect` leaves out `access-posture`, and `accounts[*].vuln_scanning` when it leaves out `vuln-scanning`. Each has a `not_shared` gap, and the gaps inside it are dropped. v0.7.1 wrote them whatever `collect` listed.

## v0.7.1

- The collector is built on epack v0.10.1.
- `artifacts/aws.cloud-posture.json` has `accounts[*].iam`, `accounts[*].vuln_scanning`, and `workforce_sign_in` again, as deprecated blocks that epack v0.10.1 declares. They hold the values v0.6 wrote, taken from the detailed artifact, at every level. Profiles that read them grade as they did before v0.7.0. A later minor removes them.
- Each of those values is also in the access-posture or vuln-scanning file, except `iam.saml_provider_count`, `workforce_sign_in.mfa_source`, and `vuln_scanning.unpatched_pct`, which have no new field.

## v0.7.0

- The collector is built on epack v0.10.0. The detailed artifact moves from `artifacts/aws.json` to `artifacts/aws.details.json`, the path epack's `ArtifactPath` gives it. A reader of the old path needs the new one
- `artifacts/aws.cloud-posture.json` no longer has `accounts[*].iam`, `accounts[*].vuln_scanning`, or `workforce_sign_in`, since `evidencepack/cloud-posture@v1` no longer has them. Its storage, database, network, logging, backup, and threat detection values are unchanged. The detailed artifact keeps its `iam`, `identity_center`, and `account_security.inspector` values as they were.
- Each run writes `artifacts/aws.access-posture.json`, in the `evidencepack/access-posture@v1` format with `system_type` `cloud`, and `collect` lists it as `access-posture`. Its sections total every account, and from the audit level `scopes` lists each account alone. Below the audit level it holds present flags and percentages, and from the audit level it adds the counts.
- The IAM user values moved to the access file. `iam.users_present`, `user_count`, `mfa_user_count`, and `mfa_coverage_pct` are now `members.local_members_present`, `local_member_count`, `local_mfa_member_count`, and `local_mfa_coverage_pct`. Every IAM user can sign in with its own password or access keys, so every one counts as local. The same users are also `members.members_present` and `member_count`.
- `iam.root_mfa_enabled` is now `root.root_mfa_coverage_pct`, which still counts a root user with no password, access key, or signing certificate as covered. `root.root_access_keys_present` says whether a root user has an access key. `iam.root_access_protected` is now `root_mfa_coverage_pct` at 100 with `root_access_keys_present` false.
- `iam.access_keys_present` and `access_key_rotation_compliant_pct` are now `credentials.credentials_present` and `rotation_overdue_pct`. The credentials are the active access keys, so the counts are of keys, where the old ones counted users. `rotation_overdue_pct` is the share of keys last rotated more than 90 days before the run, which inverts the old rule.
- `iam.saml_providers_present` and `workforce_sign_in.in_use` are now `sign_in.sso_configured`. It is true for an account with an active organization instance of IAM Identity Center, an `AWSReservedSSO_` role, or a SAML provider. The total is false when any account's is false, left out when any other is unknown, and true otherwise. `workforce_sign_in.user_count` is now `members.sso_member_count`, and it is 0 when no account has Identity Center. Identity Center users are not IAM users, so `member_count` leaves them out. `workforce_sign_in.mfa_source` and `iam.saml_provider_count` have no new field.
- The access file adds the inactive members, whose password and access keys were all last used more than 90 days before the run, or never. It also adds the unused and never-expiring access keys. AWS access keys never expire, so `never_expiring_pct` is 100 whenever there is one.
- The access file's admins are the IAM users with the AWS managed `AdministratorAccess` policy, attached to the user or to one of the user's groups. They are read with a new `ListAttachedUserPolicies` call for each IAM user, and `ListGroupsForUser` and `ListAttachedGroupPolicies` calls for the user's groups. The calls need `iam:ListAttachedUserPolicies`, `iam:ListGroupsForUser`, and `iam:ListAttachedGroupPolicies`.
- Some access values are never reported by AWS and are left out with an `unsupported` gap. They are `sign_in.sso_required`, `mfa_required`, and `scim_enabled`, the external member values, and `members.sso_coverage_pct`.
- Some values AWS reports are not read, and are left out with the new `not_read` gap. Its detail names the call that would supply the value. They are the unrestricted and write access credential values, which need the users' policy documents, and `connected_apps`. So are each account's `sso_member_count` in `scopes`, and the container resource values where ECR scanning is off.
- Each run writes `artifacts/aws.vuln-scanning.json`, in the `evidencepack/vuln-scanning@v1` format, and `collect` lists it as `vuln-scanning`. It has an Amazon Inspector entry each for `hosts`, `containers`, and `functions`, with coverage and open findings by severity. A finding is overdue when it is rated critical and was first observed more than 30 days before the run, or rated high and first observed more than 90 days before it. cloud-posture's `vuln_scanning.enabled` is now the `hosts` entry's `enabled`, read from Inspector itself where it came from Security Hub. Its `unpatched_pct` and the counts behind it have no new field.
- The vuln-scanning values come from new Inspector calls in each scanned region. Whether Inspector and each scan type are on comes from `BatchGetAccountStatus`. `ListCoverageStatistics` and `ListFindings` are called only where Inspector is on. The calls need `inspector2:BatchGetAccountStatus`, `inspector2:ListCoverageStatistics`, and `inspector2:ListFindings`. The run does not fail when Inspector is off or one of these calls fails.
- Every AWS call declares the IAM action it needs, and the GitHub identity token call declares `id-token:write`. The result lists each one with its call as `permission`, at every level. A gap from a denial whose message names the action names it as `missing_permission`, unless a policy denies it explicitly.
- A `collect` list that leaves out `access-posture` or `vuln-scanning` skips the calls only that file needs.
- `docs/schema/methods.json` gives an `x-epack-method` sentence for each value of the access and vulnerability files.
- A DB instance or Aurora cluster encrypted with an AWS owned key now counts as encrypted at rest. Its storage has `StorageEncrypted` false and `StorageEncryptionType` `sse-rds`. The detailed file's `storage_encrypted`, `encrypted_at_rest`, and `encrypted_at_rest_database_count` values change with it. So do cloud-posture's `database.encrypted_database_count` and `encryption_pct`.
- A Lambda function with code scanning on now counts once in the vuln-scanning file's `functions` entry. Such a function has a PACKAGE and a CODE coverage entry in Inspector, and only the PACKAGE entry counts now. Where code scanning is on, `scanned_resource_count` and `coverage_pct` drop. Both were left out as `invalid_response` when the double count passed `resource_count`, and they are now written.
- The detailed file's credential report row for the root user leaves out `password_enabled`. The report has `not_supported` in that column for the root user, and it used to read false. `root_password_present` says whether the root user has a password.
- With `regions` set and no IAM Identity Center instance in the listed regions, the detailed file's Identity Center values are now left out with a `not_read` gap. An instance is listed in the region where Identity Center was enabled, and that region may not be listed. The access file's `sso_member_count` is left out too. So is `sso_configured`, unless a role or SAML provider shows SSO. They read 0 and false before.
- When an account has an account instance of IAM Identity Center beside the organization instance, the organization instance's values are now reported. Before, `sso_configured` read false and `sso_member_count` read 0 when the account instance was in an earlier region.
